# B：GitHub（代码托管平台）上的调研保存与接手方案

查阅日期：2026-11-12（亚洲上海时区）。范围：为 B 比较“模型写文件、自动提醒、自动捕获、程序拦截”四类机制。没有安装或运行这些项目，没有测量实际遵循率，也没有据此批准新增脚本或改写 B 的既定取舍。

## 问题与结论

问题：能否减少外部调查结果只留在聊天中，以及换会话后找不到决策依据的情况？

核对了三个项目的当前默认分支代码，并通过远程引用取得下面的提交编号。链接固定到这次核对的版本，不以持续变化的分支链接作为唯一依据。

| 项目 | 核对提交 | 主要机制 | 与 B 的关系 |
|---|---|---|---|
| planning-with-files（以文件保存规划与发现） | `51bf62def62d1cb317d37936929b4ef97cf862c3` | 提示词要求及时记发现；生命周期脚本注入上下文、提醒；可选结束拦截 | 最接近“别忘记及时落盘”，但不证明调研内容合格 |
| GitHub Spec Kit（规范驱动开发工具集） | `979b0a3c1277283371c9901ad0eed04b64a99997` | 规划阶段汇总决策、理由、备选方案；实施阶段按存在情况读取调研 | 最接近“让调查成为规划材料，并进入下游入口” |
| claude-mem（跨会话记忆工具） | `cbcf471f33ab8355c221851f822ab9222f313e4f` | 工具事件自动送入记录渠道，由观察代理形成记忆与摘要，下次会话注入索引 | 减少手工保存依赖，但不是任务级决策依据报告 |

限定结论：在这次检查的文件里，没有看到能机械判断“来源真实支撑当前决定、重要未知已经解决”的通用检查。不能由此推断整个 GitHub 都没有这种方案，也不能把其他项目的存在当作有效性实验。

## 1. planning-with-files：提示词加自动提醒，可选结束拦截

已核实：

- [技能源文件](https://github.com/OthmanAdi/planning-with-files/blob/51bf62def62d1cb317d37936929b4ef97cf862c3/.agents/skills/planning-with-files/SKILL.md) 将 `findings.md` 用于调查和发现，要求在每两次查看、浏览、搜索后保存关键发现；重大决定前重新读取计划。这是给模型执行的规则，不是“两次搜索以后检测报告质量”的程序逻辑。
- [自动触发脚本](https://github.com/OthmanAdi/planning-with-files/blob/51bf62def62d1cb317d37936929b4ef97cf862c3/skills/planning-with-files/scripts/skill-hook.sh) 的工具调用后分支输出更新进度和阶段状态的提醒；脚本注释及正常执行路径说明它返回成功。提醒被注入不等于模型已写文件。
- [结束检查脚本](https://github.com/OthmanAdi/planning-with-files/blob/51bf62def62d1cb317d37936929b4ef97cf862c3/skills/planning-with-files/scripts/check-complete.sh) 默认是建议性报告。显式开启对应模式后，结合进行中阶段、重复拦截上限和进度变化等条件输出阻止结束的决定。
- [结束事件分发脚本](https://github.com/OthmanAdi/planning-with-files/blob/51bf62def62d1cb317d37936929b4ef97cf862c3/skills/planning-with-files/scripts/gate-stop.sh) 将宿主的结束事件交给上述可选检查。它检查阶段完成状态，不是逐项核实调查来源或结论。

可借鉴：在执行过程中按时提醒，减少只在规划开头读过一次规则后遗忘。不能照搬的推论：不能因为存在“阻止结束”就说它保证调研质量。固定每两次操作写一次适合防遗忘，但是否适合 Trellis，需要评估噪声和写入成本；本轮不决定采用这个频率。

## 2. Spec Kit：调查形成决策材料，下游显式读取

已核实：

- [规划指令](https://github.com/github/spec-kit/blob/979b0a3c1277283371c9901ad0eed04b64a99997/templates/commands/plan.md) 在调查阶段把未知问题转换为调查任务，再写入 `research.md`。要求保存选择的方案、理由、考虑过的备选方案；文字上要求调查完成后进入设计。
- [实施指令](https://github.com/github/spec-kit/blob/979b0a3c1277283371c9901ad0eed04b64a99997/templates/commands/implement.md) 在加载实施上下文时，将 `research.md` 列为存在时读取的材料。保存和消费两端都有入口。
- [前置条件脚本](https://github.com/github/spec-kit/blob/979b0a3c1277283371c9901ad0eed04b64a99997/scripts/bash/check-prerequisites.sh) 对实施计划和按参数要求的任务清单执行结构性检查；`research.md` 被归入可选材料清单。该脚本没有因为调研不存在而统一拒绝，更没有验证来源是否支持结论。

可借鉴：让调查结论直接服务决策，同时把下游读取入口写清楚。不能据此称为“调研强门禁”：规划指令中的必须要求和脚本实际拒绝条件是两回事。

## 3. claude-mem：自动捕获，观察代理整理，跨会话检索

已核实：

- [项目说明的工作原理](https://github.com/thedotmack/claude-mem/blob/cbcf471f33ab8355c221851f822ab9222f313e4f/README.md#how-it-works) 描述工具调用交给本地服务，观察代理形成短记录和会话摘要，新会话获取索引并按需取详情；记录保存在本地数据库。
- [自动触发配置](https://github.com/thedotmack/claude-mem/blob/cbcf471f33ab8355c221851f822ab9222f313e4f/plugin/hooks/hooks.json) 的 `PostToolUse`（工具调用后事件）把调用交给观察处理器，并启用异步执行。
- [观察处理器](https://github.com/thedotmack/claude-mem/blob/cbcf471f33ab8355c221851f822ab9222f313e4f/src/cli/handlers/observation.ts) 传递工具名称、输入、响应和会话等信息，存在跳过条件；本地暂存或服务记录后允许主流程继续。不是每个平台、每类调用都无条件捕获。

可借鉴：把原始活动的捕获交给程序，避免完全依赖工作模型记得保存。需要区分：事件记录是程序捕获，哪些内容形成有效记忆仍涉及观察模型。自动记忆不是“这个任务为什么选这个方案”的权威记录，也不能直接替代 B 的任务目录文件和引用。对 Trellis 而言，增加完整记忆服务明显超出当前仅修改指导文字的范围。

## 对 Trellis 的建议与待决定项

1. 可以保留 B 的轻量方案，借鉴 Spec Kit 的“决策、理由、备选”和“下游显式读取”。本次调查支持它是已有实践，不能证明仅靠提示词足以满足预期可靠性。
2. 如果用户要求“模型忽略提示也不能悄悄漏掉”，仅修改规划技能不够。可另讨论工具事件后的自动提醒或原始来源记录，但需要先确认宿主事件覆盖和成本，不能从这三个项目直接推导为所有 Trellis 平台通用。
3. 程序可检查文件存在、引用可定位、是否有显式调研状态等客观条件；“关键证据是否充分”仍需审阅。客观结构检查与语义审阅应分别说明保证范围。
4. 本轮不推荐安装任一项目，不新增依赖、不改脚本、不把提示词路线或自动触发路线替用户定案。

## 检索方法与限制

- 先尝试仓库接口获取结构，遇到访问额度限制；改为网页检索、固定提交的原始源码及 `git ls-remote` 核对默认分支引用。
- 来源均为项目自身文档或源码。只读核对，没有执行外部脚本，也没有验证其在当前机器、当前会话宿主上的运行效果。
- 不能把默认提醒、显式可选拦截、自动记录和内容质量检查混为一类；上述比较是源代码行为分析，不是三者优劣的实测排名。
