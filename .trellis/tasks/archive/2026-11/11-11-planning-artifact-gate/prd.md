# A：开工前规划材料检查与变更复核

## 当前结论和授权范围

状态：规划中。本会话已确认下面三条产品原则，并授权整理需求、设计、实施及测试计划；尚未进行最终规划审阅，尚未授权实施。命令、字段和流程细节是本次技术设计，不能倒写成用户已经逐项批准。

1. 每个任务首次开工前都有 `prd.md`、`design.md`、`implement.md`，内容可以很短，不能由模型自行按“简单任务”省略。
2. 开工确认对应用户看过的材料版本。确认之后、开工之前发生实质变化，必须展示变化并再次取得确认。
3. 实施中发生实质变化，暂停受影响工作，更新规划并重新确认后继续；按原要求编码、补测试、修实现错误可以继续。

父任务：[任务材料可靠性与可追溯性](../11-12-task-artifact-reliability/prd.md)。B 已迁至[调研依据保存与交接](../archive/2026-11/11-12-research-evidence-handoff/prd.md)，C 位于[归档记录对应提交](../11-12-archive-commit-provenance/prd.md)。本任务不重复实现 B，不提前实施 C。

## 原始问题

文件齐全不等于方案正确，也不等于用户批准了当前版本。现有 `task.py start` 主要检查角色上下文清单，可能在缺少规划材料、材料为空或记录损坏时进入实施。仅增加指纹，只能检查“文件有没有变”，仍无法证明三份内容一致，或证明用户确认了变化后的方案。

目标是让正常工作流留下可检查的版本、审阅和变更记录，把漏材料、拿旧版确认开新版、实施中偷偷改方向这三种错误变得可见。这里采用轻量命令检查加明确审阅流程，不建立宿主级写入封锁或可信身份系统。

## 当前要求

| 编号 | 要求与验收边界 |
| --- | --- |
| R1 | 首次从 `planning` 进入 `in_progress` 时，三份材料必须是可读的 UTF-8 非空白文本。分别说明做什么、如何解决及为什么、执行和验证步骤。不设最低字数、强制章节、占位词黑名单或语义评分。空文件拒绝；只有标题或重复正文等质量问题由审阅发现。 |
| R2 | 保留 `task.py attest <dir> --note "说明"`，在 `meta.planningAttest` 保存三个文件的 SHA-256 内容指纹、时间、非空说明及待审版本。先统一换行再计算，细节见设计。声明只表示模型已核对，不代表用户批准。 |
| R3 | 最终审阅前固定待审版本，向用户展示目标、方案、步骤、验收、风险和变化。实际开工绑定该版本，记录用户答复及其可回查出处；模型重新声明不能替代用户确认。程序必须拒绝缺少版本对应、版本不符和无确认说明的首次开工。确认出处属于可审计声明，不是程序验证过的身份凭据。 |
| R4 | 实质变化包括范围、对外行为、解决方案、兼容性、风险、验收或步骤含义改变。必须生成新的待审版本，旧确认不得覆盖。纯排版、错别字等可记录为非实质修订，保留原确认；程序检查修订链，模型负责判断是否确实不改变含义，用户或审查者可核对差异。 |
| R5 | 实施中实质变化先暂停受影响工作，返回规划，写清变化、影响和依赖，再更新相关材料、审阅并重新确认后恢复。真正独立且在原授权范围的工作可继续，但不得把依赖受影响方案的工作称作独立。正常实现与按原要求修错不触发重新确认。此条替代历史 R5 的“实施中不覆盖”边界。 |
| R6 | 新检查在所有首次开工路径生效，包括无会话身份的降级路径；在状态、分支、会话指针和 `after_start` 钩子等副作用之前拒绝不合格输入。损坏、缺失或未知状态不能当作兼容任务绕过。规划检查无绕过开关；`--allow-empty-context` 只控制原上下文清单。 |
| R7 | `validate` 与 `start` 复用同一结构及版本检查。规划期校验可以表示“材料版本可送审，仍等待用户确认”，不得因尚无批准而形成无法送审的循环，也不能把校验成功说成已获准开工。已实施任务的普通恢复保留原上下文清单规则。 |
| R8 | 普通恢复已有 `in_progress`、`review` 任务不强迫历史补档；带新版规划记录的任务必须检查漂移。旧任务发生实质变更后进入新复核流程，并在恢复前具备三份材料。`create` 的会话定位仍保持 `planning`，不代表实施；`completed` 不能重新开工。归档仅追加规划警告，不新增规划阻断，不改变原有归档检查。 |
| R9 | `create` 继续只生成需求初稿，不自动生成空设计或空计划。保留任务记录未知键、其他 `meta` 字段和原子写入方式；失败不伪报成功。两份脚本目录保持逐字节一致。 |
| R10 | 所有发货工作流、技能、平台提示、状态提示和生成器统一取消“三文件按轻重任务分流”；保留与规划文件无关的轻量描述。状态提示能显示真实版本、声明说明和待确认/已确认/漂移/回规划状态，并指向检查命令。生成副本从来源更新，不手改掩盖生成器遗漏。B 的调研保存、核查、交接规则必须保留。 |
| R11 | 提供可重复的命令测试、提示与生成测试、变更复核演练及同条件旧新对照。按场景列出旧结果、新结果、预期差异、退出码和副作用，不用总通过率混淆共同旧失败或计算无依据的改善百分比。 |

## 不承担的保证

- 指纹不证明设计满足需求；文档短不代表差，文件多不代表规划好。
- 模型可能错误地把实质变化称作文字修订，或编造确认说明。没有可信宿主审批事件，本方案只能检查记录和流程条件，不能保证授权不可伪造。
- 不阻止绕过 `task.py` 直接写文件，不为每次编辑弹审批，不自动识别语义变化。
- 不批量追补历史任务，不改任务创建许可规则，不引入新的顶层任务状态，不实现 C 的提交来源机制。

## 验收与对应材料

[design.md](design.md) 定义命令、数据、状态转换与能力边界；[implement.md](implement.md) 定义实施批次和文件；[测试计划](research/test-plan-2026-11-12.md) 将 R1—R11 对应到自动测试和人工演练。全部验收前不得称 A 完成。

必须能演示：极小任务仍三份齐全；甲版确认后实质改乙版并重新声明，仍必须重新确认；只改错别字能保留确认且留下版本链；实施中改变验收后暂停、回规划、再次确认再继续；旧任务单纯恢复无补档要求。每种拒绝都检查状态、分支、指针和钩子没有先改变。

## 产品决定来源

- 本会话用户“是的，同意”：开工确认后材料有实质变化，要展示变化并再次确认。
- 随后用户“可以”：统一三份、内容可短、不能按任务简单程度省略。
- 随后用户“同意”：实施中实质变化暂停受影响工作、更新规划并重新确认；正常按原要求执行可继续。
- 最新用户“可以”：整理上述原则对应的完整规划材料。任务继续 `planning`，不视作开工许可。
